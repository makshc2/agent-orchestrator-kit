## Why

Tier 1 має окремі regression-тести, але немає відтворюваної таблиці класів дефектів артефактів, які `gate-check --review` ловить або пропускає. Після explore від 2026-10-29 потрібен детермінований baseline для оцінювання майбутніх покращень гейтів; джерело контексту — `docs/course-derived-plan-2026-10-29.md`, розділ 2.

## What Changes

- Додати eval на `node:test`, який копіює чисті фікстури, вносить по одній мутації та викликає CLI `gate-check --review --json`.
- Використати синтетичну фікстуру і заморожену адаптацію однієї реальної заархівованої зміни з власними main specs та описом походження.
- Зафіксувати `task_contract: strict`, очікувану діагностику й причину для кожної мутації; відрізняти виявлений дефект від випадкового падіння процесу.
- Виводити таблицю `caught / missed`, окремо позначаючи відомі прогалини. Регресія обов'язкового виявлення падає; відома прогалина сама по собі не падає.
- Включити міжзмінну колізію MODIFIED як вимірювану прогалину, не додаючи її детектор.

## Capabilities

### New Capabilities

- `artifact-mutation-evals`: ізольований корпус мутацій, перевірка результатів Tier 1 та відтворюваний звіт у стандартному тестовому запуску.

### Modified Capabilities

Немає. Вимоги до поведінки `tiered-review` і `task-contract` залишаються чинними.

## Impact

Новий `test/artifact-mutation-evals.test.js` і `test/fixtures/mutations/`. Наявний `npm test` автоматично підхоплює файл. Використовуються вбудовані API Node.js та вже встановлений локальний OpenSpec; нових залежностей, змін runtime CLI чи шаблонів IDE немає.

## Non-goals

- Новий лінт семантичної якості `Done-when:`: заборона `openspec/specs/task-contract/spec.md:101` лишається чинною; видалення поля перевіряє лише наявну структурну перевірку.
- LLM-виклики, LLM-judge, оцінювання Tier 2 чи випадкові мутації.
- Новий детектор міжзмінних колізій, зміна schema verdict або JSON-виводу gate-check.
- Експорт `runTier1Review`, рефакторинг гейтів, нові npm-команди чи CI workflow.
- `spec-verify-conformance-report`: наступний окремий change, де треба врахувати `head -200` і відповідність номерів рядків оригінальним файлам.

## Acceptance criteria

- Обидві немутовані фікстури проходять справжній локальний OpenSpec validate і Tier 1 у strict-режимі; кожен mutant запускається зі свіжої копії.
- Корпус містить структурні дефекти proposal/tasks/delta, пошкоджений MODIFIED-заголовок, відсутній scenario та відомі прогалини семантики Done-when і міжзмінного MODIFIED.
- `caught` вимагає exit 1, `pass: false` і діагностику очікуваного класу; crash, timeout, невалідний JSON і непов'язані помилки не зараховуються як успіх.
- Відомі `missed` видимі у звіті без падіння тесту; перехід прогалини в коректно виявлену проблему також не падає. Пропуск дефекту з обов'язковим виявленням падає.
- Звіт містить колонки ID, профіль, фікстуру, клас дефекту, очікування, фактичний результат і причину та підсумок caught/total для цього корпусу; baseline не входить у знаменник; за invalid чи baseline failure звіт позначає incomplete і не виводить caught/total.
- Цільовий `node --test test/artifact-mutation-evals.test.js` і загальний `npm test` виконують eval без мережі, LLM, записів у робочі артефакти або залежності від живого архіву.
