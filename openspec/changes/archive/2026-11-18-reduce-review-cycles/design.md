## Decisions

1. **Самоперевірка, а не лінт.** Суперечність між `Do:` і `Done-when:` (як «обгорнути всі три» проти «рівно два») є семантикою природної мови: `Done-when:` є довільною shell-командою або фразою, а `Do:` довільним описом. Детермінований детектор дав би або хибні спрацьовування, або пропуски. Тому контролем є чекліст architect: (a) після будь-якої правки `Do:` перечитати `Done-when:` цього й залежних тасків; (b) кожне твердження «X існує / відсутнє / на рядку N» про код перевірене читанням файлу, а `path:line` записано поруч у артефакті чи design; (c) кожну grep-умову з `Done-when:` прогнано проти поточного коду, очікуваний результат досяжний. Звіт має `**Self-check:** done | not applicable` (`not applicable`: change без тверджень про код і без grep-умов). «Read narrowly» доповнено: читання для верифікації дозволене, діапазонами рядків.
2. **Done-when.** Перевага поведінковим умовам (`node --test test/<file>`, спостережувана поведінка). `grep` лише для нечислової наявності/відсутності; «рівно N» / «exactly N» заборонені, якщо таск не пояснює, чому точне число гарантоване. Приклад bad: `Do:` обгортає всі три присвоєння, `Done-when:` вимагає рівно двох входжень; приклад good: `Done-when:` запускає тест, що перевіряє всі три присвоєння.
3. **Reviewer.** `review.md` отримує блок `## Task verdicts` (рядок на таск `<id> | ✓/✗ | причина`) і список усіх blockers за один прохід. Авторство блока обов'язкове для reviewer; необов'язковим є лише його enforcement скриптом: `checkReviewMd` блок не вимагає, старі review.md і шаблони лишаються валідними. Повторне review: спершу кожен Previous finding (resolved/unresolved + evidence), потім ПОВНИЙ наявний чекліст Tier 2 (збережена вимога main spec «Повнота повторного review і той самий клас дефекту»), додатково rescan тих самих LLM-only класів. Обмеження «той самий клас» належить лише додатковому скану: воно не скорочує чекліст і не охоплює класи Tier 1.
4. **Blocker проти решти.** `Required Before Apply` містить лише blockers: (a) таск неможливо виконати; (b) конфлікт із main specs чи Non-goals; (c) суттєва суперечність між proposal, design, tasks і delta specs (таск виконуваний, але приписує протилежне до delta); (d) поведінка design без покриття в delta чи tasks. Це узгоджено зі збереженими вимогами повного скану (main spec tiered-review, «Повнота…», quick-режим). Major/Minor, які виконавець apply виправляє в межах однозначного затвердженого контракту Files/Do/Done-when (без вибору між варіантами), іде в `## Fix During Apply`, також коротко в `apply-notes.md` (≤ 20 рядків, пріоритезує reviewer). Без blockers вердикт APPROVE; на RC секція теж може бути і переноситься. `checkReviewMd`: секція необов'язкова, але якщо є, не порожня (`review.md: "Fix During Apply" section is empty`). Невиправний виконавцем пункт іде в наявний escape valve.
5. **Fast-fix (`pipeline.review_fast_fix`, типово `off`).**
   **Парсинг.** `reviewFastFix` true лише для точного скаляра `on`. Секційний шлях: `values.review_fast_fix === 'on'` (readYamlScalar вже прибирає коментар і лапки, тож `onion` дає false). Legacy-шлях (конфіг без блока `pipeline:`): окремий якірний regex рядка `/^[ \t]*review_fast_fix:[ \t]*(on|off)[ \t]*(?:#.*)?$/m` замість префіксного збігу, тож `onion`, `online`, `on-ish` не дають `on`; інші ключі legacy-читача не змінюються. Ключ є в усіх `orchestrator.yaml` з коментарем.
   **Придатність.** Лише коли (1) ключ `on`; (2) `review.md` має Verdict REQUEST CHANGES, конформний за `gate-check --review-md` і з секцією Checklist, тобто прийнятий Tier 2 RC (запис Tier 1 `**Source:** gate-check` без Checklist непридатний: схема відхиляє APPROVE для такого запису, `bin/agent-orchestrator.js:3665`, `test/review-md-gate.test.js:137`; це не змінюється); (3) `Required Before Apply` називає 1–2 таски. Conductor перевіряє (1)–(3) і лише тоді додає в spawn-prompt інструкцію fast-fix. Architect остаточно оцінює «без змін `design.md` і delta specs» і повертає `**Fast-fix:** eligible (tasks: <ids>) | ineligible (<reason>)`. При `ineligible` або відсутній інструкції діє звичайний re-propose (architect виправляє все потрібне, next command `/opsx:review <name>`).
   **Межі architect.** Змінює лише `tasks.md` і створює/оновлює `apply-notes.md` (≤ 20 рядків; виняток із правила, що файл пише reviewer: потрібен, бо `checkReviewMd` вимагає його на APPROVE, а перший RC його не має), запускає `gate-check --review <name>`, повертає exit code в `**Gate:**`.
   **Життєвий цикл conductor (propose).** Allowlist після звіту розширюється рівно на кроки нижче; нормальний шлях `off` без змін. (a) `gate-check --review` exit 0 і `Fast-fix: eligible`; (b) явне підтвердження користувача (AskUserQuestion); (c) в одному shell-виклику: копія `review.md` у тимчасовий файл, заміна значення єдиного рядка `Verdict:` на `APPROVE (fast-fix, approved by user)`, додавання `## Fast-fix` (дата запису, id виправлених тасків, `gate-check --review exit 0`, примітка «Tier 2 пропущено, незалежна перевірка відсутня»), `gate-check --review-md <name>`; на exit ≠ 0 копія повертається на місце; (d) успіх: Output і Session Exit дають next command `/opsx:apply <name>` у новій сесії, `fast-fix` у Decisions handoff; відмова користувача, `ineligible`, збій `--review-md` або `gate-check --review` ≠ 0 після одного re-spawn: `review.md` лишається RC без змін, next command `/opsx:review <name>` (при red gate `## Blocked` і `/opsx:propose <name>`, як зараз). Те саме дзеркально в SKILL propose; `agent-orchestration` SKILL (routing review → apply) отримує виняток: RC → propose → apply лише за цим протоколом.
   **Вердикт і гейти.** Читачі вердикту (`parseReviewVerdict`, archive readiness, Gate 1, gate-check, handoff, recovery, hooks) приймають `^APPROVE`; їх НЕ змінюємо. Hook-перевірки зберігають вимоги до чистого commit і актуальності вмісту, суфікс тексту сам по собі їх не задовольняє. Запис вердикту conductor є прийнятим винятком із «parent MUST NOT сама писати вердикт», на кшталт T1-запису.
   **Тести.** Фікстури: прийнятий Tier 2 RC із переписаним Verdict, `## Fast-fix` і `apply-notes.md` ≤ 20 рядків проходить `checkReviewMd`; без `apply-notes.md` або з > 20 рядків падає; Tier 1 запис із APPROVE падає; тексти propose/SKILL/orchestration/architect закріплюють кроки життєвого циклу (не лише слово `fast-fix`).
   **Ризики:** побічні ефекти правки `tasks.md` не рецензовані; незалежну перевірку пропущено; `apply-notes.md` може застаріти (тому його оновлює architect); вердикт APPROVE фактично видає користувач, а не reviewer. Описано в design, коментарі конфігурації й CHANGELOG.
6. **Підказка розміру.** Понад 8 тасків або 4 і більше delta specs: architect пропонує розбиття на два changes у `**Risks:**`, не блокує. Цей change: 10 тасків і 2 delta specs; перевищення порогу свідоме (більшість тасків: правка шаблонів і тестів); можливий поділ: зріз A (CLI, конфіг, reviewer/apply, architect-правила) і зріз B (fast-fix).

## Risks / Trade-offs

- Самоперевірка залежить від дисципліни LLM; Tier 1 її не бачить (свідоме рішення).
- Fast-fix послаблює незалежність review, лише за явного `on` і підтвердження користувача.
- Тести закріплюють фрази шаблонів: змінюються `test/smoke.test.js` (`new state is present` у блоках `:227`, `:754` лишаються; додаються нові фрази), `test/instruction-text-consistency.test.js`, `test/review-md-gate.test.js`, `test/gate-check-config-parser-and-src-glob.test.js`, `test/conductor-protocol-templates.test.js`.
