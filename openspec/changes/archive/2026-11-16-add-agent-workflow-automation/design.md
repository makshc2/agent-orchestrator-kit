## Context

Apply is parent-driven (`templates/.agents/commands/opsx-apply.md`); subagent-only guards would miss most edits. `apply-test-discipline` explicitly excludes CLI test gates and permits disclosed narrowed runs, empty commands and user-accepted existing failures. `gate-check --staged` uses staged diffs and implicit change discovery, so it cannot serve as a pre-edit authorization primitive. Update generates mirrors/wrappers but asks users to run a separate shell sync. Legacy sync uses broad deletion, including whole Claude command directories. Existing GitHub/GitLab workflows already offer opt-in after-merge archive.

## Goals / Non-Goals

**Goals:** verifiable freshness, bounded optional workflow enforcement, scoped background checks, safe automatic IDE delivery and actionable local outcomes.

**Non-Goals:** another runtime, adapter protocol, semantic snapshot writer, approval source or CI archive implementation. No auto-approve, task ticks, auto-commit, merge, publishing, external messages, fleet rollout or Phase 4. Legacy unflagged sync retains its existing contract.

## Decisions

### 1. Extend the shipped runtime; the v1 contract is frozen

`add-agent-hook-runtime` is merged and archived. Its contract (`docs/agent-hooks.md`, section "Extension contract"; code in `bin/hooks/index.js`, `bin/hooks/store.js`, `bin/hooks/binding.js`, `bin/hooks/policies/{context,recovery}.js`) is used as-is; nothing is renamed or extended. Apply preflight only confirms these exports still exist and stops for a plan amendment if one is missing.

- **Events:** EventV1 `{schemaVersion:1, kind, eventId, occurredAt, scope:{repoId,worktreeId,changeId,sessionId,agentId}, contextEpoch, source, data:{role,taskId,files,tool,outcome,stopReason}}`. Workflow policies use `tool.before`, `tool.after`, `file.changed`, `agent.end`, `session.end`.
- **Policies:** `PolicyV1 = {id, events?, evaluate(event, ctx)}` returning ResultV1 `{context[], findings[], decision}` with decision `allow|deny|followup|null`. Workflow modules are added to the static `builtinPolicies` array in `bin/hooks/policies/index.js` (today `[recoveryPolicy, contextPolicy]`); adapter event protocols are untouched; only their shared configuration reader changes.
- **`ctx`** is exactly `{capabilities, config, store, storeFor, signal, notify}`; `ctx.config.projectDir` is the project root. `ctx.notify({code,message})` appends once per code per dispatch to the `diagnostics` namespace of the default store.
- **Store:** `createStore({projectDir, scope:{level,...ids}})` with async `read(ns,key)`, `transact(ns,key,fn)`, `append(ns,record)`. Levels form the hierarchy `worktree -> session -> agent`; `change` is orthogonal and needs an explicit `changeId`. The default `ctx.store` is the agent level when session and agent ids are both non-null, otherwise the session level; a null session id (or null agent id at agent level) yields a quarantined store keyed by event id with a diagnostic, never coarsened. `ctx.storeFor(level)` re-scopes. `worktree` is one shared namespace for every writer, including null-session events, and never quarantines.
- **Namespace placement (level / namespace / key):** at `worktree` (`worktreeStore` in `bin/hooks/binding.js`): `jobs` / `lease` and `jobs` / `queue` (atomic identity-keyed envelopes and startup reservation), `owned-sync` / `manifest` (owned-sync manifest) and the existing `bindings` / `binding-tokens`. At `change` (`createStore` with `level:'change'` and the bound `changeId`, helper `changeStore` in `bin/hooks/workflow/stores.js`): `verification-evidence` / `<sha256-16 of base command + actual command + scope>` plus `verification-evidence` / `latest`, and `completion-intent` / `<sha256-16 of session + agent + task>`. At the default session/agent store (`ctx.store`): `followup-budget` / `<intent key + work epoch>` and per-session suppression marks. Evidence and intent records are local workflow state: they never enter the `audit` or `diagnostics` namespaces, which keep the runtime rule of no command arguments. A policy that sees `store.quarantined` or an unbound change records a finding and takes no effect.
- **Binding:** `hooks bind --change --role --task --session [--agent]` stores the binding (roles `implementer|test-writer|code-writer|design-implementer|conductor|implementation|testing`) with the task's contracted Files; a child links only with a single-use `--token` (`aok-bind-...`, TTL at most 1 hour) and resolution is by exact session/agent identity via `resolveBinding`, so a child never inherits the parent's binding implicitly. Missing identity stays unknown.
- **Decisions:** dispatch applies a decision only when global `hooks.mode` is `enforce`, `hooks.policies.<id>.enabled` is `true`, that entry's `mode` is `enforce`, and the capability for the event kind has `deny: true` (for deny) or `followup: true` (for followup); otherwise it adds a `policy.decision.downgraded` advisory finding. Dispatch drops any decision when `stopReason` is `user_cancelled` or `outcome.status` is `cancelled`; workflow policies additionally return no decision for unknown, error or paused stops. `stopReason:completed` alone does not establish apply completion.
- **Capabilities (CapabilitiesV1 `events[kind].{supported,injectContext,deny,followup,reason}`):** Claude has `tool.before` deny, no `agent.end` followup and no `file.changed`; Cursor has `tool.before`/`agent.start` deny, `agent.end` followup, `file.changed`, but no `session.resume` or `context.reset`; Amp has `tool.before` deny and `agent.end` followup but no `file.changed`, `session.resume`, `session.end`, `context.compacting` or `context.reset`. Unverified client payload shapes force every `deny`/`followup` to false. Gaps yield findings and manual fallbacks, never a claim of enforcement; on Claude, edit-driven jobs use `tool.after` write paths instead of `file.changed`.
- **Configuration:** Extend `parseHookConfig` in `bin/hooks/install.js` to isolate direct hooks keys from policy keys and preserve `hooks.policies.<id>.{enabled,mode,options}`. Defaults remain disabled/observe, absent options `{}`. The supported options syntax is a single-line JSON object (valid YAML flow syntax), parsed with JSON.parse at the exact policy indentation; multiline YAML options, malformed values or wrong types produce a configuration finding and disable that policy, never silently discard options. No dispatcher option interpretation is added. `readHooksConfig` in `bin/hooks/adapters/shared.js` also reads the direct `pipeline.require_spec_review` boolean, default true for absent/invalid values, into `ctx.config.pipeline.require_spec_review`; comments/nested lookalikes cannot disable review. Bind/CLI and workers use the same reader. Five shipped YAML files retain six disabled/observe entries.
- **Policy-owned option schema:** verification: `timeoutMs` (default 30000), `ignoredInputs`, `generatedOutputs`, `environmentNames` (string arrays, default empty); completion: `validationTimeoutMs` (30000); scope: `{}`; checks: `commands` (default empty array of `{id, executable, args, globs, writablePaths}`), `debounceMs` (500), `timeoutMs` (30000); owned-sync: `target` (`all|cursor|claude|amp`, default all), `debounceMs` (500), `timeoutMs` (30000); workflow-notifications: `dedupMs` (60000). Timeouts must be integers 1..300000, debounce 0..5000, dedup 1..300000; paths must be relative and constrained by binding Files. No command inference. Each handler validates its own options before effects.
- **Disabled means no effects:** a common wrapper in `bin/hooks/policies/workflow.js` checks `ctx.config.hooks.enabled === true` and the individual entry's `enabled === true` before invoking any of the six handlers. Disabled/absent entries produce the empty ResultV1 without evidence invalidation, intent/budget writes, queueing, spawning, sync or notification. This does not change dispatch arbitration. Workers re-read configuration before executing queued policy work; disabling a policy cancels its pending work without running it. Explicit CLI commands are deliberate user operations, independent of automatic policy enablement.
- **Policy wiring:** six PolicyV1 objects delegate to workflow handlers. Write hooks only invalidate evidence and enqueue configured scoped checks or owned sync. Full verification is exclusively `hooks verify`; neither writes nor completion validation runs `verifier.test_command`. End events enqueue fingerprint-only completion validation. Slow execution and hashing stay outside the 1500 ms dispatch budget; installed local Node entry points avoid network/npx.

### 2. Command evidence describes a real execution

Add `hooks verify --change <name> --session <id> [--agent <id>] [--narrow-command <command> --reason <text>]`. The base command is exactly `verifier.test_command`; no package-manager guess. Narrowing must record a resource restriction and actual scope. Runner invokes configured commands from the project root with timeout and captured exit/signal, retaining at most the last 20 output lines for immediate reporting. Persistent audit stores IDs, command digests and status, not raw command arguments/output. A local evidence record may store the configured/actual command text only as a reference to local configuration plus digest; secret-bearing overrides require redacted display and digest-only storage.

Fingerprint sorted path/type/mode/index-stage+blob/content digests for every tracked file and nonignored untracked file by default, plus explicit ignored inputs. Always include verifier config, command definitions, relevant lockfiles and config files. Include declared environment-variable digests (not values), Node/tool versions, platform and worktree identity. Exclude hook state, declared generated outputs, and explicitly listed active-change progress artifacts (handoff/checkpoint/metrics/decisions) from test inputs; hash the task contract with checkbox state normalized. Keep separate raw task/handoff digests for completion freshness. Code, configs, locks and task contract text cannot be excluded by this progress rule. Exclusion changes invalidate evidence and are disclosed, so writing the required handoff or ticking the final task does not force an endless test rerun. Narrow execution never silently narrows the input fingerprint. Record pre and post hashes using a retry-bounded stable enumeration/read; mismatch, read error, timeout or concurrent mutation makes evidence nonreusable. Before reuse recompute current inputs, command and execution scope; HEAD is metadata only. A change during a run remains a possible race; hooks do not claim transactional isolation of external writers.

Evidence status separates success/failure/narrowed/skipped-no-command/not-run/accepted-preexisting-failure. Store base and actual command digests, scope, timing, counts only when observed, and reason. No-command skip remains acceptable with warning. Accepted failure retains the real nonzero exit, named failure, baseline evidence and authorization receipt. Validate the receipt against an actual user-role message from a supported host's local transcript or user-channel API, binding its ID/digest to the named baseline failure. Never trust an agent-supplied boolean or an unverified acceptance string. Unsupported provenance leaves automated acceptance unresolved and directs the existing manual workflow; it never fabricates authority.

### 3. Completion intent and handoff freshness

Add `hooks complete --change <name> --session <id> [--agent <id>] [--task <id>] [--confirm-handoff]`. Resolve the exact binding; optional task is only a cross-check. Missing/mismatching bindings record nothing. `--confirm-handoff` is the explicit producer: after reading the semantic handoff, the conductor confirms that it describes the latest substantive work. Without this flag an existing receipt must pass validation; capturing an old file at completion never creates a receipt implicitly. The CLI does not write semantic prose.

In the change store, `completion-state/<intentKey>` holds `{workEpoch,lastOutcomeSeq,receipt,validation}` and `completion-intent/<intentKey>` holds the identity and current raw tasks/handoff digests. A receipt contains `{changeId,sessionId,agentId,taskId,handoffDigest,tasksDigest,inputDigest,workEpoch,lastOutcomeSeq,confirmedAt,confirmationId}`. CLI confirmation hashes current inputs outside dispatch under the shared lease, after the latest evidence outcome; exact identity, digests and sequence must match on reuse. An old byte-identical handoff without explicit confirmation is rejected; explicit confirmation can renew unchanged prose, because it asserts semantic review rather than a filesystem write. Runtime snapshots and mtime never supply this receipt.

`hooks complete` synchronously performs bounded current fingerprint validation, compares evidence command/scope and receipt, stores intent/validation and prints all findings, including Claude parent Stop/followup gaps. Every genuine completed end event queues a NEW fingerprint-only validation with that event ID, reports pending (never trusts a prior CLI snapshot), and may request the single corrective follow-up when supported/enforced. The worker reads current input/task/handoff digests before and after validation; any drift, including an external write after CLI registration, yields stale/unresolved. It persists a local completed/blocked outcome for notification, never injects a new turn itself. Thus success is asserted only for the worker's stable validation interval; later external writes remain a documented race, not a claim of isolation. Slow validation failure/timeout is unresolved, not reusable success. An end event never asserts success from cached evidence. Unsupported clients use the synchronous CLI findings/manual workflow and no background continuation.

The intent is identified by intentKey (session, agent, bound task) and persists across work epochs; an edit advances workEpoch within the same intent and neither replaces nor closes it. Budget state lives in default session/agent `followup-budget/<intentKey + workEpoch>`: at most one follow-up per epoch, and a hard cap of two follow-ups per intent (bound task/session) across epochs, counted under `followup-budget/<intentKey>-total`. A repeated failure inside one epoch releases control. Increment workEpoch only for a distinct observed non-worker tool.after edit within bound task Files after intent creation, excluding generated/progress paths and tracked job-origin writes; deduplicate by eventId. Fingerprint changes, repeated complete/verify/confirm commands and worker edits do not reset it. Unknown-origin edits conservatively do not reset it. Late external edits still stale evidence without granting another budget. User cancellation/manual stop/error clears pending continuation and cancels validation generation. Discussion/partial work create no intent. Existing handoff/archive/gate-check do not read evidence or run tests.

### 4. Explicit scope and approval currency

Scope policy uses exact bound task Files, role and canonical allowed roots. Export `approvalRevision(projectDir, changeName)` in `bin/recovery-sources.js`, returning `{state,verdict,reviewSha,reviewDigest,digest,files}`. It requires an APPROVE verdict using the existing verdict reader, clean committed review.md and `reviewCurrency` current; currency alone is never approval. Use the union of committed/current planning paths including proposal.md, design.md, optional design-brief.md, tasks.md (checkbox-normalized) and specs/**/*.md; additions/deletions matter. Unknown/stale/rejected reviews cannot create approval. Bind and child-token linking recompute current approval; store `{reviewSha,reviewDigest,digest,files}` only when approved/current, otherwise null.

Every intercepted edit re-reads current verdict, review bytes/commit and planning content (no first-edit or mtime-only cache). Require current APPROVE and equality of reviewSha, reviewDigest and planning digest against the binding. Deleting, dirtying or committing REQUEST CHANGES revokes authorization even with unchanged planning content; re-review with another reviewSha requires explicit rebinding. With file-backed `pipeline.require_spec_review: false` skip only approval checks, not identity/path checks. Unknown reads or deadline exhaustion return unresolved scope findings/deny subject to existing arbitration, never a cached approval. Parent and linked child retain separate exact bindings.

**Conductor progress writes.** The parent must still tick checkboxes (`pipeline-subagents`) and write `handoff.md` (`session-handoff`), neither of which is in a task's Files. The scope handler therefore grants a narrow progress allowance, evaluated after the Files check fails and never a blanket `openspec/` exemption. It applies only when the exact session/agent binding is a parent binding: created by direct `hooks bind` (`via: 'explicit'`, no `--token` link) with role `implementer`, `conductor` or `implementation`; `implementer` is the role the apply twins and docs/agent-hooks.md bind for the parent, so the allowance and the shipped bind name the same identity and no twin or docs change is needed. A child binding (token-linked, `via` other than `explicit`, or a direct bind with role `test-writer|code-writer|design-implementer|testing`) never receives it, so a child ticking tasks.md or writing handoff.md is denied as outside Files. The allowance covers exactly two canonical paths of the bound change, `openspec/changes/<boundChangeId>/tasks.md` and `openspec/changes/<boundChangeId>/handoff.md`, resolved through symlinks; any other change directory, any other artifact of the bound change (proposal.md, design.md, design-brief.md, specs/**, review.md, decisions.md) and path escapes are denied. For tasks.md only checkbox toggles are permitted: pre-edit the handler allows the path; where the tool payload shows the proposed text it denies a non-checkbox change, and in all cases tool.after reconciliation compares the checkbox-normalized task-contract digest with the binding's approval digest and records a scope-violation outcome on mismatch (approval then reads stale and later edits are denied until rebind and re-review). Identity checks and live approval currency (unless review is disabled) still apply to the allowance; checkbox normalization keeps approval current, handoff.md is outside the approval digest. The allowance does not tick tasks by itself: autonomous ticking stays out of scope, the parent performs the edit.

For visible write paths enforce denies unbound/unknown scope, stale approval or forbidden role/path with an actionable reason; observe only reports. Never infer the newest change by mtime or call staged gate-check as authorization. Shell/MCP paths may be unknowable: record a coverage gap and reconcile observed changed paths afterward without destructive rollback. Git/CI remains independent. This is workflow assistance, not a sandbox.

### 5. One bounded worktree mutation queue

Use one atomic worktree `jobs/queue` record containing `{jobs,reservation}`. Each job envelope includes `{jobId,kind,repoId,worktreeId,changeId,sessionId,agentId,taskId,bindingDigest,allowedFiles,paths,commandId,optionsDigest,originJobIds,createdAt,deadline,generation,status}`. `jobId` indexes the record directly. The coalescing key hashes kind + full identity + bindingDigest + allowedFiles + commandId + optionsDigest; different changes/tasks never merge. Keep one pending successor per key while a generation runs; additions merge into that successor. Sync CLI jobs may have null session/task but use the same worktree lease; automatic bound-task checks require complete identity. Revalidate binding, options and allowed scope before execution.

`withLease({projectDir,ids,ownerToken?,timeoutMs}, fn)` is the only service acquisition boundary. Without a token it atomically acquires `jobs/lease` `{owner,expiresAt}`, renews every 1s (5s TTL), and releases in finally; with a token it validates the live same-worktree owner and runs fn without reacquiring/releasing. Verification, checks, ownedSync and completion hashing all accept this token. Loss of lease aborts child execution and prevents patch/manifest commits. Verification is an exclusive barrier, not a second read-lock design. CLI wait is bounded by timeout (default 30s).

`ensureWorker` does not spawn while a live lease/reservation exists and otherwise atomically claims a 5s startup reservation in jobs/queue before spawning; only the reservation winner spawns the installed `hooks worker --job <id> --reservation <token>` process. Worker renews its reservation every 1s while waiting/running and clears it on exit, verifies job lookup and reservation, waits boundedly for any CLI lease, then holds the shared lease and drains FIFO across keys, at most two generations per key and 16 jobs or 60s per worker. Each job has its configured timeout. At drain bound, release then atomically reserve/spawn a successor for remaining work; each envelope expires after at most five minutes, so this cannot perpetuate one job. Normal CLI release calls ensureWorker for queued work; enqueue, any enabled workflow event, and explicit `hooks worker --recover` also trigger recovery of expired reservations/leases. Crash recovery is bounded to 5s after such a trigger; without a later trigger no autonomous timer is promised. Failed spawn clears its matching reservation and records a finding. Concurrent starts, mixed kinds and enqueue-during-CLI cannot lose a wakeup: release and enqueue both inspect the atomic queue after publishing their state. Worker event suppression uses persisted originJobIds, never an EventV1 extension.

Run read-only checks without mutation. Formatters whose scope is not guaranteed run in a disposable working copy populated from the current tree (including uncommitted/untracked inputs); inspect their patch and import only permitted task-file changes if source fingerprints still match. On conflicting edits report and discard that import, never overwrite another agent's work. No full suite per write. A command not configured produces a visible skip, not an invented npm invocation.

### 6. Owned sync is an additive safe path

Add `sync --owned --target <cursor|claude|amp|all>` and `update --sync [--target ...]`. Both use one service and worktree mutation lease; an optional owned-sync policy enqueues it after managed-source edits. Generate instruction mirrors/Amp wrappers in staging through existing rendering logic, never the destructive legacy writer; preserve locally modified wrappers before any generation or deletion. Then create a planned destination mapping for native agents, skills, rules, namespaced commands and owned Amp settings entries. No broad rsync --delete or whole-directory removal in this path.

Manifest entries record source, destination and last delivered digest. First run adopts byte-identical counterparts or verifiably kit-generated files; unrecorded conflicts remain untouched. Delete only stale manifest-owned destinations still matching their delivered digest. Preserve user-modified owned files and foreign files, report conflicts and exit nonzero for an explicit CLI invocation; hooks report a nonblocking finding. Stage writes, use atomic renames and journal manifest transitions so crashes are recoverable. Symlink/path escape is rejected. Preserve foreign IDE JSON keys and spend-hook configuration. Legacy unflagged CLI/shell sync remains available and documented as the older mirror-all behavior; automation never invokes it. Optional `--owned` shell entry delegates locally to the safe CLI without downloads. No consumers are updated merely by implementing this feature.

### 7. Outcomes use existing local diagnostics

`bin/hooks/workflow/outcomes.js` owns an internal transport, not a new telemetry service: `worktreeStore` namespace `workflow-outcomes`, key `pending`, is an atomic bounded queue (last 256 entries, 24h TTL). `recordOutcome` producers are scope (denial/coverage), completion CLI/worker (pending/blocked/completed), checks worker (success/failure/timeout/suppression), verification runner and owned sync (conflicts/results). Each record carries unique outcomeId, full identity, policy, source event/job, status, evidence digest, freshness, verification scope, duration and reason code; no command text, output or secrets. Null identity remains null and is not attributed to another session.

The notifications policy reads matching worktree/session/agent/change records on end events; workers also call the same guarded drain after producing outcomes so late results need no future end event. It never reads another policy's ResultV1 from ctx or treats native event.data.outcome as verification. `notifyOutcome` atomically deduplicates by outcomeId and session/change/reason/time window, then writes sanitized audit and local notice. Global and notifications enabled guards apply to both paths; disabled notifications leave bounded records to expire.

Map status to allowed `status`, evidence ID to `digest`, duration to `durationMs`, reason/freshness to stable `code` (for example workflow.evidence.stale or workflow.sync.conflict), verification scope and suppression details to bounded predefined `message`, source ID to `eventId`, plus allowed scope IDs and paths. Call the existing sanitizer; do not add arbitrary freshness/scope/conflict audit keys or extend its allowlist. `ctx.notify({code,message})` serves event dispatch; out-of-dispatch drain appends sanitized diagnostics through an explicitly scoped runtime store. Coalesce blocked/completed/repeated-error notices locally, never send external messages. Document existing archive_after_merge CI without modifying authority.

## Risks / Trade-offs

- Fingerprinting large trees costs time → perform hashing outside dispatch, cache only with verified stat/content inputs and invalidate uncertain reads; report measured overhead.
- External writes can race jobs → leases cover kit work only; stable pre/post hashes and conditional patch import detect conflicts, and no universal isolation is claimed.
- Acceptance provenance varies by host → unsupported sources fall back to the existing explicit user workflow without self-approval.
- Safe sync cannot infer ownership of every old file → preserve ambiguous files and report first-run conflicts instead of deleting them.
- Enforcement can inconvenience users → off/observe defaults, one follow-up, capability checks and unconditional cancel bypass.

## Migration Plan

The runtime dependency is already merged and archived. Ship disabled policies and owned sync flags; validate in isolated fixtures for every profile (generic, mvp, node, vue3) and each client (Claude, Cursor, Amp) with its disclosed capability gaps. Explicitly trial observe mode in a consumer before opting into supported enforcement. Roll back by disabling policies; retain evidence/audit for diagnosis, and remove only owned generated content through runtime lifecycle tooling. Existing manual commands and opt-in after-merge CI continue. Twelve-project rollout requires a separate user action.

## Open Questions

No product decision blocks proposal. Supported user-message provenance and platform enforcement variants must be pinned to tested host fixtures during implementation; unsupported variants remain manual.
