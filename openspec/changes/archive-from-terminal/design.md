## Context

Чотири попередні зміни — `fix-next-session-prompt`, `tier1-delta-heading-check`, `metrics-ledger-integrity`, `gate-check-config-parser-and-src-glob` — злиті в код (коміти e4774ef, 934a582, 3adc60c, 3f3d242), але ще не заархівовані: їхні delta-спеки лежать у `openspec/changes/<name>/specs/`, main specs їх поки не містять. Ця зміна спирається на їхній код (секційний reader `pipeline.*`, `canonicalRole`, parent-driven промпт) і з однією вимогою перетинається за текстом (див. Ризики).

`archive` (`bin/agent-orchestrator.js`, `.command('archive <name>')`) сьогодні: валідує ім'я та `--platform`, резолвить change через `npx openspec status --change <name> --json`, далі Gate 1 (verdict у `review.md`), Gate 2 (незакриті `- [ ]`), Gate 3 (цільовий каталог вільний), sync-рішення й план, `metricsPrepareArchiveStart` (пише `pending` в активний `metrics.json`), `renameSync`, `openspec validate --all --strict` з rollback, фінальний `handoff.md` з `Next command: none` і `metricsFinalizeArchive` (ставить `archivedAt`). `status` рахує готовність inline (блокери `tasks incomplete`, verdict, `design-brief`). `readPipelineConfig` повертає п'ять ключів; для `archive_after_merge` читача немає. Persist-гілка `handoff <name>`: `fieldsFromSections` → `missingHandoffFields` → `parseTasksProgress` → `buildNextSessionPrompt` → `process.stdout.write(prompt)`; усі інші повідомлення йдуть у stderr. `firstLineCommand` повертає перший рядок цілком, коли токена `/opsx:` немає, тож shell-рядок у `## Next command` переживає повторне читання `handoff.md`.

Докази (9 архівних `metrics.json` v2): 9 змін, 61 сесія, 12 Archiver-сесій — 11,5 хв роботи й 7 405 683 вхідних токенів, приписаних Archiver-рядкам (за аналізом плану — переважно leftover чужих сесій). `fix-metrics-session-attribution`: 61,9 с / 41,4 с / 46,2 с «відкладених» чатів і справжній archive на 1,4 с. Про Gate 0 чесно: з поточним кодом `archivedAt` з'являється лише після переміщення в `archive/`, а фінальний `handoff.md` з `Next command: none` пишеться в архівній папці, тож обидва маркери трапляються в АКТИВНОМУ каталозі лише у скопійованій чи «воскрешеній» архівній папці. Gate 0 — детермінована страховка, а не лікування спостереженого збою; типовий повторний запуск (папку вже переміщено) і далі закінчується наявною помилкою `could not resolve change` — це поза обсягом.

## Goals / Non-Goals

**Goals:**
- Нормальний шлях archive — команда в терміналі, яку після зеленого apply друкує CLI; окремий чат для archive не потрібен.
- `archive` детерміновано відмовляє для каталогу, що вже виглядає заархівованим, без хибних відмов (повторне ім'я зміни, відсутній чи зіпсований `metrics.json`).
- CI-режим `--if-ready` з тим самим визначенням готовності, що й `status`; skip — не помилка, справжній збій — гучний.
- `pipeline.archive_after_merge` читається; `status` його показує.
- CI-архівація — лише opt-in; `/opsx:archive` лишається тонким fallback-ом.

**Non-Goals:**
- Відмова другого persist у 10-хвилинному вікні, clamp `startedAt`, зміни `metricsPrepareArchiveStart`/leftover.
- Gate 4 або інший гейт archive за вмістом `metrics.json` (крім Gate 0 за позитивним свідченням); R2b; R5-lite.
- Зміни `buildNextSessionPrompt`, `handoff --restore`, `openspec-howto`, `spec-workflow-openspec`, `opsx-quick.md`, `spec-archiver.md`.
- CI-архівація за замовчуванням, новий прапорець `init`, окремий workflow-файл, видача bot-токена.
- Версія, release, `init --force` / `update` / `sync` у корені кіта.

## Decisions

**D1. Зелений apply визначає CLI, а не агент.** У persist-гілці `handoff <name>`, після `missingHandoffFields` і `parseTasksProgress`, але до `buildNextSessionPrompt`, `isGreenApplyExit(fields, progress)` перевіряє: `canonicalRole(fields.closedRole) === 'Implementer'`; `progress.total > 0 && progress.done === progress.total`; `## Blocked` порожня за суворим переліком (`none`, `none.`, `-`, `—`, `n/a`, `немає`; регістр ігнорується, один маркер списку `- `/`* ` і кінцева крапка зрізаються; будь-який інший текст — не порожньо). Будь-який сумнів дає поточну поведінку (промпт) — безпечний напрямок. У зеленому стані `fields.nextCommand = archiveCommandLine(name)` (`npx agent-orchestrator-kit archive <name> --sync`), `fields.nextRole = 'none'`, `fields.prompt` — той самий рядок, stdout — рівно цей рядок і `\n`; `handoff.md` пишеться звичайним `buildHandoffMarkdown` (рядок у бектиках у `## Next command`, fenced блок `## Prompt`). Next command агента перекривається (stderr-нотатка, коли відрізнявся) — інакше результат лишився б залежним від LLM. Підказка в stderr (запустити в терміналі після merge, `/opsx:archive` — fallback) замінює «Copy the prompt below…», бо блоку для вставки в новий чат немає. Тригер не залежить від `archive_after_merge` (прапорець керує `status`/CI, а не тим, що друкує handoff) і від мови (рядок — shell-команда); повторна генерація `--no-metrics` дає той самий результат, бо eligibility перераховується з тих самих `tasks.md` і `handoff.md`.
Альтернативи відкинуто: (a) довіряти лише Next command, заявленому агентом — залежить від LLM, а ціль — детермінований CLI; (b) тригер лише за станом тасків — спрацював би для Architect/Reviewer-фікстур, у яких усі таски відмічені; (c) правити `buildNextSessionPrompt` під короткий вихід — бюджет EN-промпта 1 528 із 1 536 байт і закріплений перший рядок `/opsx:…` (тест «prompt skeleton stays within the size budget»), тож гілка живе в handoff-action, а не в білдері.

**D2. Gate 0: позитивне свідчення в АКТИВНОМУ каталозі, до будь-якого запису.** `findArchivedMarker(changeRoot)` читає `metrics.json` (валідний JSON + `archivedAt` — непорожній рядок) і `handoff.md` (`## Next command` після `firstLineCommand` дорівнює `none` без урахування регістру). Виклик стоїть одразу після `existsSync(changeRoot)` і **до** Gate 1, sync-запису та `metricsPrepareArchiveStart`, тож відмова не лишає ні змін main specs, ні фантомного `pending`/leftover/сесії. Відмова — stderr `already-archived gate failed — change "<name>" is marked as archived (<маркер>). If this folder is a re-opened copy, clear "archivedAt" in metrics.json or set a real "## Next command" in handoff.md, then re-run archive.`, exit 1. Fail-open: відсутній файл, помилка читання, невалідний JSON, `null`/порожній `archivedAt` — не свідчення. Прапорця-обходу немає (`--force` лишається лише підтвердженням `--no-sync`).
Альтернативи відкинуто: (a) детекція за наявністю `openspec/changes/archive/*-<name>` будь-якої дати — повторно використане ім'я зміни дало б хибну відмову (явне застереження плану); (b) читати `## Metrics` — суперечить spec «Гейті archive не залежать від metrics.json», тому вимога змінена вузько (Gate 0 читає `## Next command` і `archivedAt`, ніколи `## Metrics`); (c) прапорець-обхід — відкриває шлях до повторного архіву, а відновлення і так одне: стерти маркер.

**D3. `archive --if-ready`: skip замість помилки, готовність — одна на `status` і CI.** `commander` `--if-ready` → `opts.ifReady`. Після валідації імені та `--platform` і `existsSync(changeRoot)` команда читає `config = readPipelineConfig(...)` (рядок переїхав угору з Gate 1) і для `--if-ready` перевіряє по порядку, до будь-якого запису: (1) `config.archiveAfterMerge === false` → `skip: archive_after_merge is false`; (2) Gate 0 → `skip: already archived — <маркер>`; (3) `archiveReadinessBlockers(changeRoot, config)` непорожній → `skip: not ready — <блокери через "; ">`. Skip — `console.log` одного рядка, `process.exitCode` не чіпається (exit 0). Інакше йде звичайний archive: Gate 1–2 повторно підтверджують готовність, а Gate 3, sync-конфлікти й rollback валідації завершуються exit 1 — справжні збої в CI мають бути гучними. Без `--if-ready` Gate 0 відмовляє (exit 1), а `archive_after_merge` не читається: людина завжди може заархівувати вручну. `archiveReadinessBlockers(changeDir, config)` — рівно та inline-логіка, що була в `status` (`tasks incomplete` для відсутнього/порожнього/неповного `tasks.md`; `review verdict "…" (need APPROVE)` або `no review.md` при `requireSpecReview`; `no design-brief.md` при `requireDesignBrief` без `Design: none`; `config === null` → review обов'язковий, brief ні); `status` викликає її замість inline-блоку, поведінка й тексти без змін.
Альтернативи відкинуто: (a) парсити вивід `status` у shell або `status --json` — крихко й дублює контракт; (b) окрема команда `archive-ready` чи окремі exit-коди — більша поверхня без виграшу, а skip у `archive` читається з одного рядка; (c) продублювати логіку гейтів усередині гілки `--if-ready` — власний Gate 2 пропускає відсутній `tasks.md`, тож у CI за `require_spec_review: false` (профіль mvp) каталог explore-стадії з одним `handoff.md` було б заархівовано; `status` суворіший, тож «status каже ready ⇒ CI заархівує» лишається одним визначенням.

**D4. `archive_after_merge` читає той самий reader.** `parsePipelineLegacy` отримує `pick('archive_after_merge', /archive_after_merge:\s*(true|false)/)`, а `parsePipelineSection` уже віддає будь-який прямий дочірній ключ `pipeline:`, тому `parsePipelineConfig` додає `archiveAfterMerge: bool(values.archive_after_merge, true)` — `true` за відсутності ключа, невалідного значення чи файлу (збігається зі значеннями шаблонів), `false` лише за явним `false`; закоментований ключ і той самий ключ під іншою секцією ігноруються тими самими правилами, що й решта `pipeline.*`. `status` друкує `archive_after_merge: <true|false>` одним `log.info` під заголовком, коли `readPipelineConfig` не `null` (окремого рядка на change немає). Нове поле змінює форму об'єкта, який п'ять тверджень у `test/gate-check-config-parser-and-src-glob.test.js` порівнюють повністю (`assert.deepEqual`), тому в них додається `archiveAfterMerge: true`. Над ключем у `templates/orchestrator.yaml` і чотирьох профілях — однорядковий коментар про політику; значення не змінюються.
Альтернатива відкинута: окрема функція `parseArchiveAfterMerge`, яку `readPipelineConfig` дописує до результату, — лишила б `parsePipelineConfig` неповним і подвоїла б прохід по секції; чесна ціна — п'ять однорядкових правок очікувань.

**D5. Archive з терміналу не потребує змін у metrics-коді.** `resolveRestoreClient` без env клієнта дає `platform: null`; `metricsFinalizeArchive` пише сесію `Archiver` із `platform: null`, `spendSource: "unreported"`, без токенів; stderr-попередження (`metrics: archive client unknown …`, `session.model is null`, `spend.costUsd is null`) не впливають на exit code; `metricsPrepareArchiveStart` і leftover не чіпаються. Зафіксовано сценарієм і тестом (exit 0, `archivedAt`, `pending: null`, Archiver `platform: null`, наявна сесія Implementer без змін). Стара stderr-підказка «run archive from Cursor/Amp/Claude» лишається (косметичне розходження, див. Ризики).
Альтернативи відкинуто: прапорець `--terminal`; переписування leftover для терміналу — зайве, бо без клієнта collect не запускається.

**D6. `/opsx:archive` — fallback.** `templates/.agents/commands/opsx-archive.md` переписано на ≤ 1 KB (зараз 1 210 байт; ліміт тесту 1 536): абзац «нормальний шлях — термінал/CI; ця команда лише коли це було неможливо чи CLI відмовив» з посиланням на `.agents/rules/session-handoff.mdc` (вимога «Спільні Session Start/Exit блоки живуть в одному rule») і поясненням, що `archive` сам пише фінальний `handoff.md`; чотири кроки (ім'я; sync-рішення; виклик CLI з показом stdout; на exit ≠ 0 надрукувати відмову й зупинитись без ручного merge/move); без підрядка `spec-archiver`. `spec-archiver.md` не редагується (fallback без CLI зі своїм кроком самозвіту); skill `openspec-archive-change` отримує мінімальні правки (нормальний шлях і Gate 0, рядок виклику CLI збережено).
Альтернативи відкинуто: видалити команду (non-goal); лишити повний Session Exit у команді (CLI вже пише фінальний handoff).

**D7. Шаблон apply.** `opsx-apply.md` (Session Exit та рядки «suggest archive» / «You can archive this change with `/opsx:archive`») і двійник `openspec-apply-change/SKILL.md` вимагають: коли всі таски `[x]` і build/lint зелені — `## Blocked` = `none`, `## Next command` = буквальний `npx agent-orchestrator-kit archive <name> --sync`, `## Next role` = `none`; `handoff <name>` тоді друкує лише цей рядок, який і є «промптом» для вставки (перший рядок не `/opsx:…`). Інакше Next command лишається `/opsx:apply <name>` або `/opsx:propose <name>` (escape valve із записом прогалини в `## Blocked`). Archive у apply-чаті не стартує ніколи. Оскільки CLI сам перекриває Next command (D1), вимога до агента — узгодженість `handoff.md`, а не умова працездатності; `## Blocked` = `none` агент пише обов'язково, бо це частина тригера.

**D8. Тексти правил із жорстким бюджетом.** Правки мінімальні й дослівні (блоки тасків 4.3–4.5). `session-handoff.mdc`: крок 6 Exit отримує виняток для зеленого apply, абзац «Archive exception» — згадку terminal/CI і fallback; шаблон копіюється `cp` у `.agents/rules/session-handoff.mdc` кіта (рівність перевіряє тест `templates agree with the parent-driven protocol`; `init --force` не запускається). `agent-orchestration.mdc`: рядок маршрутизації `/opsx:archive` — «(fallback) — terminal/CI: …» (слово `spec-archiver` лишається), абзац Exit — виняток для зеленого apply, закріплені підрядки Exit і Start зберігаються. Запас бюджету вузький (always-apply 11 734 із 12 000 символів), тому приріст цих двох файлів обмежено 200 символами й міряється до і після (блоки тасків дають +178). Решта: `AGENTS.md` (2 904 із 4 000), `CLAUDE.md`, skill `agent-orchestration` (маршрутизація, секція «verify → archive», виняток для першого рядка в двох описах Exit, пункт чек-листа), `openspec-guide.md` (термінальна команда замість твердження про автоархів CI) і `subagents/session-handoff.md` (крок 5 persist). Не редагуються: `openspec-howto`, `spec-workflow-openspec`, `buildNextSessionPrompt`, `spec-archiver.md`, самозвіт `## Metrics` (R2b), `opsx-quick.md`.

**D9. CI opt-in: окремий job, умова за змінною, готовність вирішує CLI.** GitHub: job `archive` — `needs: verify`, умова push у default-гілку + `vars.AOK_ARCHIVE_ON_MERGE == 'true'`, `concurrency: agent-archive` без скасування, `permissions: contents: write` (потрібно лише для fallback на `github.token`), власний `actions/checkout` з `fetch-depth: 0` і `secrets.AOK_ARCHIVE_TOKEN || github.token` — окремий job, бо збережені облікові дані checkout-а `verify` перебили б токен із bypass при push. Кроки: встановлення залежностей за lockfile, цикл по `openspec/changes/*/` (крім `archive`) з `archive "$name" --sync --if-ready`, далі bot-ідентичність git, `git add -A openspec`, вихід 0 за `git diff --cached --quiet`, інакше коміт `chore(openspec): archive merged change [skip ci]` і push у default-гілку. GitLab: job `agent-archive` — `extends: .agent-verify-base` (image і встановлення залежностей), `needs: ["agent-verify"]`, `rules` за `$AOK_ARCHIVE_ON_MERGE == "true"` на default-гілці, push через `oauth2:${AOK_ARCHIVE_TOKEN}`. Коментар біля кожного job-а пояснює змінну, токен (bypass захищеної гілки), `[skip ci]` проти циклу й дефолтність терміналу. Наявні `verify`, `.agent-verify-base`, `agent-verify` не змінюються (spec «GitLab CI fragment agent-verify»). Архівний коміт містить фіналізований `metrics.json` і є останнім комітом зміни.
Альтернативи відкинуто: окремий opt-in workflow-файл на кшталт `spec-verify.yml` — більша поверхня (прапорець `init`, шлях `update`), тоді як умова за змінною дає той самий opt-in; кроки в job-і `verify` — його збережені облікові дані checkout-а перебивають bot-токен; парсити готовність у YAML — дублює гейти.

**D10. Документація.** README (розділ Archive, коментар у блоці Configuration, CLI reference, абзац «Deterministic gates») і CHANGELOG (пункти всередині наявних блоків `### Added` / `### Changed` секції `[Unreleased]`, без нових підзаголовків і bump версії) — тексти в тасках 6.1–6.2. Розділ «Changelog» самого README описує випущені версії й оновлюється під час релізу.

**D11. Spec-дельти.** Нові вимоги — `lean-archive` (Gate 0, `--if-ready`, CI opt-in, archive з терміналу), `session-handoff` (зелений apply), `orchestrator-cli-controls` (читання `archive_after_merge`). MODIFIED лише там, де текст main specs інакше суперечив би поведінці: `lean-archive` «Тонка команда opsx-archive» (fallback) і «Гейті archive не залежать від metrics.json» (вузький виняток Gate 0 за позитивним свідченням; відсутні/зіпсовані файли й далі ніколи не причина відмови); `session-handoff` «Next-session prompt follows agent_language» (сценарій apply exit; текст вимоги скопійовано з MODIFIED-версії в pending-дельті `fix-next-session-prompt`, змінено лише цей сценарій), «Session Exit вимагає самозвіт метрик у `## Metrics`» (сценарій Archiver: `/opsx:archive` — fallback без самозвіту, самозвіт лишається в `spec-archiver`) і «Persist Memory and handoff on session exit» (одне речення: зелений apply — єдиний виняток із формату першого рядка); `pipeline-subagents` «Conductor must delegate specialist work» (речення про archive і сценарій «Archive без субагентів»). Решта MODIFIED-блоків скопійована дослівно з main specs, заголовки збігаються байт-у-байт. Вимогу «CLI команда gate-check» не чіпаємо — її змінює pending-дельта `gate-check-config-parser-and-src-glob`.

**D12. Тести — один новий файл.** `test/archive-from-terminal.test.js` має власні хелпери (ізольований env, `init --profile …` у temp dir, openspec-stub зі `status --change … --json`, що віддає `changeRoot` і шлях `tasks.md`, як у smoke) і 27 тестів у вісьмох групах за префіксом назви (`config:`, `status:`, `gate0:`, `if-ready:`, `terminal:`, `green-apply:`, `templates:`, `ci:`), щоб кожен таск перевіряв свою групу через `--test-name-pattern`. Два `ci:`-тести парсять YAML пакетом `yaml` (він у `node_modules` як залежність devDependency `@fission-ai/openspec`; імпортується динамічно лише в цих двох тестах). `test/smoke.test.js` не змінюється: жодне наявне твердження не суперечить новій поведінці (handoff-фікстури там — Architect, archive-фікстури не мають маркерів Gate 0).

## Risks / Trade-offs

- [Порядок архівації: ця зміна копіює MODIFIED-вимогу «Next-session prompt follows agent_language» з pending-дельти `fix-next-session-prompt` і змінює в ній лише сценарій apply exit] → `fix-next-session-prompt` MUST бути заархівований ДО `archive-from-terminal`. У зворотному порядку sync замінює вимогу цілком, тож пізніший archive `fix-next-session-prompt` мовчки поверне старий сценарій (заголовок збігається в обох порядках, Tier 1 і `archive --sync` конфлікту не покажуть). Constraint-рядок у `tasks.md`; порядок для pending-змін: `tier1-delta-heading-check`, `gate-check-config-parser-and-src-glob`, `metrics-ledger-integrity`, `fix-next-session-prompt`, потім `archive-from-terminal`.
- [Gate 1 у корені кіта] → Для довідки: у корені кіта немає `.agents/orchestrator.yaml` (`readPipelineConfig` → `null` → review обов'язковий), а чотири pending-зміни не мають `review.md`, тому `archive` для них зараз відмовляє на Gate 1; це поза цією зміною. Ця зміна після apply потребуватиме власного `review.md`.
- [Промпт обмежений розміром і закріпленим текстом] → `buildNextSessionPrompt` не чіпаємо (EN-скелет 1 528 із 1 536 байт, перший рядок `/opsx:…`); виняток для першого рядка живе в handoff-action, у `opsx-apply.md` і в тексті правил.
- [Закріплений текст і бюджети] → Тести, що тримають текст: `templates agree with the parent-driven protocol` (3 кроки Session Start, рівність кореневого rule, закріплені підрядки `agent-orchestration.mdc`, рівно два входження «no separate Memory MCP read step» і 6 кроків Start у SKILL.md), `always-apply rules stay within a context budget`, `init installs the lean archive command…` (≤ 1 536 байт, без `spec-archiver`), `init installs orchestration…` (слова маршрутизації), `propose runs Tier 1…`, `review punch-list…`. Правки текстів дослівні за блоками тасків; кожен таск запускає ці тести.
- [Історична вимога `kit-ci-verify` «Template workflow залишається без змін»] → Вона прив'язана до change `add-kit-ci-verify` («WHEN change `add-kit-ci-verify` застосовано») і про multi-PM, lint і build шаблону; їх не чіпаємо, лише додаємо job, тож вимога лишається правдивою.
- [Cursor `sessionEnd`-hook може дописати leftover у ЛОКАЛЬНИЙ `metrics.json` після persist і дати конфлікт із CI-комітом, що переміщує папку] → Тому CI лише opt-in; README радить лишати архівну копію; термінальний archive (дефолт) такого конфлікту не створює.
- [CI-archive потребує токена з bypass захищеної гілки; два швидкі merge можуть дати non-fast-forward push у першого запуску] → Збій гучний (job червоний), наступний push у default-гілку повторює archive, або archive з терміналу; README це описує. Після `update` у consumer-репо з'являється неактивний job (у GitHub видно як skipped).
- [Хибна відмова Gate 0 на повторно відкритій папці або на `Next command: none`, яке агент записав в активний handoff] → Повідомлення називає маркер і дає відновлення; прапорця-обходу немає свідомо; для зеленого apply CLI сам пише реальну команду в `## Next command`.
- [`--if-ready` ховає неготовність за дизайном] → skip-рядок називає блокери в тих самих словах, що й `status`; справжні збої (Gate 3, sync-конфлікт, rollback) лишаються exit 1.
- [Бюджет always-apply (запас ~266 символів)] → Правки двох `.mdc` обмежено +200 символами; Done-when тасків міряє суму до і після.
- [П'ять очікувань повного об'єкта в `test/gate-check-config-parser-and-src-glob.test.js` ламаються через новий ключ] → Однорядкові правки (`archiveAfterMerge: true`) у тому ж таску, що й код (1.1).
- [Stderr-підказка terminal archive «pass --platform or run archive from Cursor/Amp/Claude» стає косметично невлучною] → Не гейт; переформулювання виходить за межі зміни (D5 — без змін у metrics-коді).
- [Після зеленого persist і наступного `--no-metrics`, коли стан уже не зелений (агент розкрив таск), `handoff.md` ще містить рядок archive в `## Next command`, який потрапить у перший рядок звичайного промпта] → Та сама ситуація, що й будь-яка ручна правка Next command: шаблон apply вимагає переписати `## Next command` у негативному стані; CLI не валідує вміст.
- [Строгий перелік для `## Blocked`] → Будь-який зайвий текст (`none (all green)`) вимикає тригер і лишає старий промпт — безпечний напрямок без втрати даних.
